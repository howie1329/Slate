Executive readout

Slate is not currently drifting into a generic productivity suite. The native model is opinionated and recognizably Slate: there is no generic status field, no project hierarchy, no tags or dependencies, no time-blocking grid, and no autonomous AI planner.

What is working: Capture / Ready / Today / Done are derived from task facts; capacity is represented in minutes; unsized Today commitments remain possible without guessed cost; Plan My Day is additive and reviewable; accepted mutations have revisions, events, and SQLite transaction boundaries.
What needs attention: the development branch has moved into Stage 3 before the Stage 2 evidence gate is closed; the full-window Board/List foundation is not yet a complete 2.0 workspace; and recovery plus anchors are treated as optional late work even though the product vision makes them part of Slate’s differentiation.
Most important implementation gap: the full-window route now renders the Planning Board or List plus Task finder, adjacent AI action, and inspector review surface. The popover still has the complete daily loop, while reversible planning movement and final desktop acceptance remain open.

Recommendation: finish the 2.0 planning foundation and its trust contract before adding Spaces, external sources, richer AI conversation, or other surface area. Promote a small, reviewable recovery loop and anchors into the near-term assisted-planning plan instead of leaving the entire recovery concept conditional.

1. Current state assessment

This assessment is based on the repository, not only the roadmap. The current branch contains the shipped 1.0/1.1 foundations plus substantial Stage 3 work.

Implemented foundations

  • Tauri macOS shell with menu-bar popover, dedicated quick-capture window, and full application window.
  • SQLite source of truth with task lifecycle, dates, estimates, ordering, revisions, and cross-window invalidation.
  • Native derived Planning projection with exhaustive Capture, Ready, Today, and Done lanes.
  • Global/weekly capacity settings, remaining minutes, over-capacity state, overflow identity, and unsized commitments.
  • Append-only planner_events ledger with source, operation, local date, and before/after values.
  • Expected-revision validation for manual writes, ordering, and reviewed Plan My Day acceptance.
  • Keychain-backed AI Assist and Plan My Day sidecar flows with transient review UI.
  • Global quick capture with draft preservation, source attribution, and revision-safe Undo.
  • Skippable onboarding, light/dark themes, compact-window behavior, and settings persistence.

Current development surface

  • Full-window Planning shell with toolbar, Board/List views, native lane projection, capacity display, filters, search, sorting, and split scrollable planning panes.
  • Task inspector with title, estimate, date, lane, completion, deletion, and stale-draft recovery.
  • Pointer and keyboard drag interactions, capacity preview, same-lane reordering, and cross-lane task mutations.
  • Desktop Task finder with lane/attention filters, enriched creation, direct keyboard creation, and bounded revision-safe task actions.
  • Read-only per-task activity history in the full-window inspector.
  • Canonical renderer adapter for Daily’s flat Today / Backlog presentation.
  • The full-window Planning toolbar now exposes the AI action and review surface; planning movement still has no user-facing Undo or equivalent operation receipt.
  • No implementation for Spaces, external sources, calendar integration, calibration UI, end-of-day review, recovery proposals, mobile, or MCP.

3. Roadmap drift and reconsideration

Sequencing drift: Stage 3 started before Stage 2 evidence. The roadmap says the next gate is Stage 2 validation and evidence gathering, and Stage 3 entry requires real use showing a need for more visual planning context. The branch already contains the full-window shell, board, lane projection, and drag interactions. This is not a thesis violation, but it means the project is making product decisions before the stated evidence gate is closed.
Recovery is too conditional for the stated differentiation. The vision names recovery/Do Less as a central part of the loop, while the roadmap makes both unfinished-day review and changed-day recovery a conditional 2.3 slot. Keep changed-day optimization evidence-gated, but make a lightweight recovery loop and end-of-day cleanup a committed post-2.0 milestone.
Anchor removal is probably the wrong default. The roadmap currently says to remove provisional Anchor state if 2.3 is not earned. The vision explicitly wants a small set of protected commitments influencing assisted planning and recovery. Keep the two-anchor limit and avoid a priority taxonomy, but move the decision to the Assisted Planning phase and wire it to a real proposal flow before deciding to delete it.
Foundation work is ahead of the evidence gate. Board/List, filters, sorting, and Task finder actions are now implemented while Stage 2 packaged/manual validation remains open. Finish parity, reversible/non-drag movement, and trust validation before expanding horizons, batch actions, or conversational AI.
Planning Session fits only as a constrained candidate. The newly added roadmap entry is directionally correct if it remains a temporary planning conversation with explicit context and reviewed proposals. It should not become a saved-chat product, a research workspace, a week planner, or a general tool-using agent.
Spaces need one additional capacity decision. The roadmap describes per-Space global/weekly capacity and an All Spaces view; the vision describes a total budget allocated across contexts. Before implementation, decide whether Space capacity is independent, allocated from a global pool, or merely a planning lens. Avoid a model that can silently double-count usable time.
Plan inventory has been reconciled. Plans 032 and 033 are now marked implemented historical records, Plans 034–038 are complete, and the plan index points the next queue at Stage 2 validation plus remaining 2.0 parity/reversibility work.

4. Missing product pieces

Core missing functionality

  • Reviewed Recovery / Do Less change set.
  • Lightweight unfinished-day / end-of-day cleanup.
  • Anchor-aware assisted planning.
  • Complete 2.0 Board + List workspace.
  • Full-window capture and AI parity with the established daily workflow.
  • Richer Plan My Day tradeoff explanation and risk context.

Supporting UX

  • Non-drag keyboard/menu alternatives for every board movement.
  • Undo or reversible receipts for manual planning movement.
  • Minimal Task Brief fields, if evidence shows title/date/estimate are insufficient.
  • Optional inline capture syntax for date and estimate.
  • Explicit context controls for any future Planning Session.

Long-term ideas

  • Spaces with a coherent total-capacity model.
  • Calendar-informed capacity proposals.
  • Sources Inbox and reviewed external candidates.
  • Calibration from accepted history.
  • Permissioned MCP.
  • Optional sync and a limited mobile companion.

The vision does not require every capture integration immediately. Shortcut capture is the proven first slice; clipboard, Share, Shortcuts, URLs, and Raycast should remain experiments until the basic capture path earns them.

7. Recommended next milestone

Close the foundation and ship a trustworthy 2.0 Planning workspace

Goal: finish the current Board/List planning foundation and restore parity with Slate’s established daily workflow before adding new product surfaces.

Why this is next: the repository already has enough native projection and UI work to make the board real, but the roadmap’s Stage 2 evidence gate is still open and 2.0’s trust contract is incomplete. This milestone reduces product and architecture risk at the same time.

Include

  • Stage 2 packaged/manual validation for quick capture, popover minimum size, AI review, persistence, and history.
  • Board/List parity verification over the exact same canonical lanes, order, task selection, inspector, and capacity.
  • Semantic cross-lane movement through a native stale-safe boundary.
  • Reversible user movement with Undo or an equivalent operation receipt.
  • Keyboard and menu alternatives for every drag action.
  • Visible capacity preview, intentional over-capacity handling, and unsized commitment behavior.
  • Full-window AI Assist / Plan My Day review through the Planning toolbar, with the compact Daily command row remaining popover-specific.
  • Popover regression at 360 × 520 and full-window empty/loading/error/reduced-motion/persistence states.

Explicitly exclude

  • Spaces and Space-aware migrations.
  • Sources Inbox, integrations, calendar connectors, sync, and mobile.
  • Planning Session, general chat, or external research.
  • Rich notes, subtasks, dependencies, tags, priority taxonomies, or a project hierarchy.
  • Productivity scores, dashboards, timers, or automatic rollover.
  • Full Recovery / end-of-day review beyond preserving the native seams needed for the next milestone.

Data and architecture

Do not add a generic status field or rewrite SQLite. Reuse the existing lane projection, order guards, task revisions, planner events, and reviewed Plan My Day change-set contract. Add a semantic movement/reversible-operation boundary only where the current ordinary task commands are not sufficient. Keep UI components responsible for intent and presentation, not lane or mutation rules.

Acceptance criteria

  1. Every non-deleted task appears exactly once in Capture, Ready, Today, or Done in both Board and List.
  2. Board and List preserve the same canonical order and selection state; alternate presentation sorting never changes persisted order.
  3. Moving work into Today shows the capacity effect before commitment; unsized work remains clearly unsized and contributes no guessed minutes.
  4. Every movement is intentional, revision-checked, atomic, and reversible; stale changes leave no partial task, order, or event writes.
  5. The full window can capture, inspect, complete, edit, plan with AI, and review proposals without making the popover unnecessary.
  6. The popover’s ordinary loop remains usable offline at its configured minimum size.
  7. npm run build, the Rust test suite, and the relevant manual desktop acceptance matrix pass.

Decisions I Need To Make

  2. Recovery priority: Should lightweight Recovery / Do Less and end-of-day cleanup become committed work immediately after 2.0, rather than remaining conditional 2.3 work?
  3. Anchor commitment: Should the current two-anchor implementation be retained and wired into assisted planning, or should it be removed if recovery evidence is weak?

  5. Space capacity: Are Space capacities independent budgets, allocations from one global budget, or planning lenses over one budget?
